# 外部自动化能力如何安全合并进控制面

2026年11月3日 · 基于一次真实合并的边界梳理。

## 一、先划清控制面已有的能力边界

控制面暴露 **8 个 MCP 工具**，其中三个和系统级 UI 自动化重叠：

| 工具 | 实际能力 | 边界 |
|---|---|---|
| `observe_ui` | 读辅助功能树，只回**节点数** | 不给可点击坐标，不回元素清单 |
| `capture_window` | 截图，**帧留在本机**，只回 `{path, nodeCount}` | 不回坐标、不做视觉分析 |
| `perform_ax` | `press` / `set_value` / `type` | **target 由调用方自己知道**，不负责"找到它" |

**所以控制面的设计取向很清楚**：它管**动作的合法性**（越界拒绝、token、回执压缩），
不管**目标怎么找**。调用方（模型）得自己知道要按哪个控件。

这个取向是对的——找目标是"感知"问题，动作是"执行"问题，混在一起两边都做不好。

## 二、外部能力该补什么、不该补什么

### 不该补（已有且更好）

| 能力 | 为什么不用补 |
|---|---|
| 执行 AX 动作 | `perform_ax` 已覆盖 press/set_value/type，且带权限校验和回执压缩 |
| 截图 | `capture_window` 已有，而且**帧不离开本机**这个设计比"回 base64"更好 |
| 令牌/授权 | 控制面的 broker token 机制已经做了，外部能力不该另起一套 |

### 该补（控制面没有，且实测踩过）

| 缺口 | 为什么重要 |
|---|---|
| **视觉复核** | AX 树有节点 ≠ 屏幕上有东西（见下） |
| **Retina 坐标换算** | 截图坐标和点击坐标差一倍（见下） |
| **语义定位** | 把"点保存"变成坐标，而不是让模型猜 |
| **环境自检** | TCC 权限会静默失效（见下） |
| **前后快照对比** | 判断"操作生效了没有" |

## 三、四个必须知道的坑（都是实测坐实的）

### 3.1 AX 树有节点 ≠ 屏幕上有东西

某 Electron 客户端：

```
AXButton  下载、安装并重启   pos=(1044,216) size=116x30    ← 位置尺寸齐全
```

按 (1102,231) 裁图出来是**一段对话文字**。应用把**已关闭浮层的 AX 节点留在了树里**。

**只信 AX，就会点在别的东西上，而且不报错。**

→ 找到元素后必须**视觉复核**：裁出 bounds，算像素方差（8×8 灰度标准差）。
实测判别力：有文字 30.4 / 有图标 19.4 / 屏幕中部 8.9 / 4×4 窄条 2.2，阈值 8.0。

### 3.2 Retina：截图坐标和点击坐标差一倍

| | 数值 |
|---|---|
| `screencapture` 截图 | 3456 × 2234（物理像素） |
| 点击可用（System Events） | 1728 × 1117（逻辑坐标） |
| 比值 | **2.0** |

把截图坐标直接拿去点，正好偏一倍——**不报错，就是点歪了**。

→ 返回值里必须带 `scale` / `logicalSize` / `coordsAre`，点击接口必须让调用方**显式声明**坐标系。
**不要把自动换算做成默认**——接口猜不出调用方给的是哪一种。

### 3.3 TCC 权限静默失效

辅助功能/屏幕录制按**二进制签名**记账。程序一重编译、签名一变，系统就当成新应用，
**不弹窗、不报错**地拒绝。

→ 动手前先跑一次环境自检，把「权限没了」和「代码写错」分开。
权限改完要**重启服务**（TCC 按进程记账）。

### 3.4 AppleScript / screencapture 的两个静默坑

```applescript
set out to out & role & "\t" & px       -- ❌ 静默失败，整个脚本返回空
set out to out & role & "\t" & (px as string)   -- ✅
```

```bash
screencapture -x -o file.png -R 0,0,300,24    # ❌ 截全屏 3456x2234
screencapture -x -o -R 0,0,300,24 file.png    # ✅ 300x24
```

两个都**不报错、返回码 0**。前者让函数返回空列表（看起来像「应用没有可点元素」），
后者让视觉验证永远拿到全屏方差（看起来像「判别力不行」）。

## 四、合并规则

外来能力要并进控制面，按这四条：

1. **不重复实现已有动词**
   动作执行、截图、令牌、回执压缩都已有。外部能力只补感知侧。

2. **不改 `src/` 主链路**
   外部能力放在独立目录（参照 `dsh-plugin/`），通过 MCP 并列挂载，
   或者作为可选依赖。主链路的编译和测试不因为它而变。

3. **回执也要压缩**
   控制面的核心设计是「回执只有退出码、失败名、diff 统计、耗时」。
   外部能力如果回一大坨（比如整棵 AX 树），会把这个设计破坏掉。
   → 回摘要 + 引用（路径/ID），细节让调用方按需再取。

4. **不许假装成功**
   「命令退出 0」「HTTP 200」「API 返回了 id」都不等于目标达成。
   - `downloads.download()` 返回 id 时**一个字节都还没下**；
   - AX 说这里有按钮，但屏幕上可能只是一段文字；
   - 截图拿到了，但可能截的是全屏而不是指定区域。
   **判据必须落在最终结果上，不是中间产物上。**

## 五、协作定位（谁做什么）

| 层面 | 谁负责 | 为什么 |
|---|---|---|
| 工作区/编辑器（文件、diff、命令、验收循环） | **控制面** | 它有 workspace 边界和命令声明机制 |
| 桌面/原生 UI（窗口、控件、键盘） | 外部能力 | 控制面目前只覆盖编辑器窗口 |
| 浏览器内部（DOM/网络/扩展） | 外部能力 | 控制面的 `capture_window` 只到截图层 |
| 动作合法性、令牌、回执压缩 | **控制面** | 这是它的核心价值，不要绕过 |
| 感知（怎么找到目标、视觉复核） | 外部能力 | 控制面明确不做这件事 |

**一句话**：控制面管「能不能做、做完怎么记」，外部能力管「在哪儿做、做没做成」。

## 六、检查清单（合并外来能力时）

- [ ] 有没有先把控制面已有能力列清楚，确认不重复？
- [ ] 改动是否只落在新目录，没有碰 `src/` 主链路？
- [ ] 回执是否压缩过（摘要 + 引用，不是全量数据）？
- [ ] 每个「成功」判据是否落在最终结果上，而不是中间产物？
- [ ] 有没有处理 Retina / TCC / AX 幽灵节点这三个环境坑？
- [ ] `npm test` 是否仍然全绿？
